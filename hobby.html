Weekend projects

01 / Character What This Looks Like

A Saturday afternoon CLI tool. A browser extension you build to scratch your own itch. A framework tutorial you follow along with. You're the only person who will ever touch this code, and the goal is learning or solving a personal problem — not shipping to users.

These projects live fast. You want to move quickly, try things, break things, and not worry about process slowing you down. The danger isn't lack of process — it's abandoning projects because you over-engineered the setup.

02 / Workflow Step by Step

Three phases. Keep it lightweight.

Day 1

  • Create a new folder and run git init — this tracks every change you make so you can always go back
  • Push to GitHub with a basic README.md explaining what the project is in one sentence
  • Enable episodic-memory and commit-commands plugins in Claude Code
  • Start building. No branches, no CI, no config files. Just code.

Before Each Feature

  • Commit what you have — even if it's messy. Small commits let you undo mistakes.
  • Use /commit to let Claude handle the commit message
  • Don't overthink structure. If it works, move on.

Before Sharing or Shelving

  • Manual test: open it, click around, make sure nothing is obviously broken
  • Update the README if the project scope changed
  • Push to GitHub so it's backed up and shareable

03 / Why Cost of Skipping

Git init on day one Without it, you can't undo mistakes or recover deleted code
Frequent commits Lose an afternoon of work to one bad refactor
Push to GitHub Laptop dies, project dies with it
README Come back in 3 months and have no idea what this project does
Episodic memory Claude forgets your entire context between sessions

05 / Prompts Setup Prompts

Copy these into Claude Code to bootstrap your project.

Project Bootstrap

Scaffolds your project with the right structure for a hobby project.

Prompt — Project Bootstrap 
I'm starting a new hobby project. Help me set it up with a lightweight structure.

Ask me these two questions, then scaffold the project:

1. What are you building? (one sentence)
2. What language/framework are you using?

After I answer, do the following:
- Initialize a git repo if one doesn't exist
- Create a README.md with: project name, one-line description, tech stack, and a "Getting Started" section
- Create a sensible folder structure for the chosen framework (keep it minimal — no over-engineering)
- Create a .gitignore appropriate for the language/framework
- Make an initial commit with the message "chore: initial project scaffold"
- Enable these plugins if not already active: episodic-memory, commit-commands

Do NOT set up:
- CI/CD pipelines
- Testing frameworks
- Branch protection rules
- Docker or deployment configs
- Linting configs (unless the framework includes one by default)

Keep it simple. I want to start coding in under 2 minutes.

Generate CLAUDE.md

Creates a project-specific CLAUDE.md so Claude understands your codebase.

Prompt — Generate CLAUDE.md 
Generate a CLAUDE.md file for this project. This file tells Claude Code how to work with this codebase.

Ask me these questions first:

1. What is this project? (one sentence)
2. What is your tech stack? (language, framework, package manager)
3. What are the most important files or directories I should know about?
4. Any hard rules Claude must never break? (e.g., "never delete the database file", "always use async/await")
5. Any external services or APIs involved?

Then generate a CLAUDE.md file at the project root with this structure:

## Workflow & Behavior
- Always commit with conventional commit messages using /commit
- Search episodic memory at the start of each session for prior context
- Keep changes small and focused — one feature or fix per session
- Don't over-engineer. This is a hobby project. Simple > clever.
- After any correction, edit CLAUDE.md so the same mistake isn't repeated
- Ask before deleting files or making breaking changes

## Essential Commands
[Fill based on tech stack — e.g., how to run, build, test]

## Architecture Overview
[Fill based on answers — brief description of folder structure and key files]

## Critical Rules
[Fill based on answer to question 4, plus sensible defaults]

Keep it concise. Under 60 lines. No boilerplate padding.
