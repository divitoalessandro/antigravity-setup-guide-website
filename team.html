Production

01 / Character What This Looks Like

A startup product with 3 developers and a staging environment. A client project where you deliver code that another team will maintain. An open-source library where strangers submit pull requests. A freelance engagement where the client expects professional delivery.

Multiple people write code, review code, and deploy code. Mistakes affect real users and real revenue. You need guardrails that prevent one person's bad day from breaking production. The process exists to protect the team from itself — not to slow anyone down.

02 / Workflow Step by Step

Full professional workflow. Every step earns its place.

Day 1

  • Initialize repo on GitHub with a clear README.md: project purpose, tech stack, how to run locally, how to run tests, contribution guidelines
  • Create a dev branch — this is your integration branch where features come together before going to production
  • Protect main — enable branch protection rules requiring PR reviews and passing CI before merge
  • Set up a full CI/CD pipeline: lint, test, build on every PR. Deploy to staging on merge to dev. Deploy to production on merge to main.
  • Establish branch naming conventions: feature/add-login, fix/cart-total, chore/update-deps
  • Generate a CLAUDE.md using the prompt below — every team member's Claude will follow the same rules
  • Enable all five essential plugins for each team member: superpowers, episodic-memory, context7, commit-commands, github
  • Agree on conventional commits — enforced via a commit-msg hook or CI check, not just a suggestion

Before Each Feature

  • Create a feature branch from dev (not from main) — feature/your-feature-name
  • Use the writing-plans skill to write a brief implementation plan — especially for features touching multiple files or services
  • Write tests first using the test-driven-development skill — define what "done" looks like before writing code
  • Open a draft PR early — this signals to the team what you're working on and invites early feedback
  • Commit frequently with conventional messages. Each commit should be a logical unit that could be reverted independently.

Before Shipping

  • Mark the PR as ready for review — add a description of what changed and why
  • Request a peer review — at least one other person reads the code. Use the requesting-code-review skill if working with Claude.
  • Ensure all CI checks pass: linting, tests, build, and any custom checks
  • Merge to dev first — let it bake in staging. Verify it works in a real environment.
  • Create a release PR from dev to main — this is the gateway to production
  • After merge to main, verify the production deployment. Monitor for errors.

03 / Why Cost of Skipping

Protected main branch One accidental force-push and production is gone
Dev branch for integration Merge conflicts pile up when everyone targets main directly
Required peer review Bugs that one person misses, another catches in 30 seconds
Full CI/CD pipeline Deploy broken code to production at 5pm on a Friday
Test coverage Refactor something and silently break three other features
Staging environment Discover environment-specific bugs only after users hit them
Branch naming conventions Five developers, five different conventions, nobody knows what's in progress
Shared CLAUDE.md Each team member's Claude generates code in a different style
Enforced conventional commits Auto-generated changelogs become useless noise

Project Bootstrap

Full project scaffold with CI/CD, branch protection, and team conventions.

Prompt — Project Bootstrap 
I'm starting a team/client project. Help me set it up with a professional structure that supports multiple developers.

Ask me these four questions, then scaffold the project:

1. What are you building? (one sentence)
2. How many people will work on this? (approximate team size)
3. What language/framework are you using?
4. Is this a fresh repo or an existing one?

After I answer, do the following:

**Git setup:**
- Initialize git repo if fresh (or verify existing)
- Create a .gitignore appropriate for the stack
- Create a `dev` branch from main
- Document branch naming convention in README: feature/, fix/, chore/

**Project structure:**
- Create a README.md with: project name, description, tech stack, how to run locally, how to run tests, contribution guidelines, branch strategy
- Create a sensible folder structure for the framework
- Add linting config (ESLint, ruff, etc.) with sensible defaults
- Set up a test runner with one example test
- Add an .editorconfig for consistent formatting across editors

**CI/CD:**
- Create a GitHub Actions workflow (.github/workflows/ci.yml) that:
  - Runs on push to main and dev, and on all pull requests
  - Installs dependencies
  - Runs linting
  - Runs tests
  - Runs build (if applicable)
- Create a separate deploy workflow (.github/workflows/deploy.yml) that:
  - Triggers on push to main only
  - Placeholder steps for deployment (I'll fill in the specifics)

**Branch protection (document, don't enforce — I'll set it up in GitHub):**
- main: require PR, require 1 review, require CI pass, no direct push
- dev: require PR, require CI pass

**Session files:**
- Create a progress.txt with sections: COMPLETED, IN PROGRESS, NEXT, KNOWN BUGS, BLOCKED (all empty to start)
- Create a lessons.md with header: "Team knowledge base — corrections, patterns to avoid, and debugging solutions. AI reads this at session start. Update after every debugging session."

**Plugins to enable for all team members:**
- superpowers, episodic-memory, context7, commit-commands, github

**Commit conventions:**
- Add a commit-msg convention note in CONTRIBUTING.md
- Format: type(scope): description
- Types: feat, fix, chore, docs, test, refactor, style, ci

Make an initial commit: "chore: initial project scaffold with CI/CD"

Do NOT set up:
- Docker (unless the framework requires it)
- Kubernetes or cloud infrastructure
- Monitoring or alerting
- Database migrations (I'll handle that separately)

Prompt — Generate CLAUDE.md 
Generate a CLAUDE.md file for this team project. This file tells Claude Code how to work with this codebase. Every team member will use the same file, so it must be comprehensive and unambiguous.

Ask me these questions first:

1. What is this project? (one sentence)
2. What is your tech stack? (language, framework, package manager, database, deployment target)
3. What are the most important files or directories I should know about?
4. Any hard rules Claude must never break? (e.g., "never commit to main", "never modify the migration files directly", "always use the ORM, never raw SQL")
5. Any external services or APIs involved? (include auth providers, payment processors, etc.)

Then generate a CLAUDE.md file at the project root with this structure:

## Workflow & Behavior
- Use conventional commits via /commit for all changes
- Search episodic memory at the start of each session for prior context
- Read progress.txt and lessons.md at the start of every session
- NEVER commit directly to main or dev — always use a feature branch
- Branch from dev, not from main
- Enter plan mode (writing-plans) before implementing anything with 3+ steps
- Use test-driven-development skill — write tests before implementation
- Open a draft PR early for visibility
- Request code review before merging using requesting-code-review skill
- Keep commits small, focused, and independently revertible
- After completing a feature, update progress.txt
- After any correction or debugging session, update lessons.md
- Verify work before marking done — tests pass, CI green, feature works end-to-end
- For complex multi-file tasks, use subagents to keep the main context window clean
- Fix bugs autonomously. Don't leave broken code for someone else.
- Demand elegance — clean abstractions, consistent patterns (skip for trivial one-line fixes)
- Ask before: deleting files, dropping tables, changing API contracts, modifying CI config, updating dependencies

## Essential Commands
[Fill based on tech stack — install, dev server, test, lint, build, deploy]

## Architecture Overview
[Fill based on answers — folder structure, key files, data flow, service boundaries]

## Data Model
[Fill if relevant — database tables, key relationships, important schemas, migration strategy]

## Development Patterns
[Fill based on stack — naming conventions, file organization, error handling, logging, API response format]

## Task Management
- Plan before building. Use writing-plans for anything touching 3+ files.
- Work one step at a time from IMPLEMENTATION_PLAN.md.
- Update progress.txt after every completed feature.
- Capture corrections and debugging insights in lessons.md.
- Reference PRD.md for product decisions, not assumptions.

## Critical Rules
[Fill based on answer to question 4, plus these defaults:]
- Never expose API keys, secrets, or credentials in code — use environment variables
- Never skip tests to ship faster
- Never bypass CI checks
- Always handle errors at API boundaries with consistent error response format
- Keep dependencies minimal and audited
- Document breaking changes in PR description
- Update README when adding new setup steps or changing how to run the project
- Simplicity first. Minimal impact changes.
- No lazy fixes — root causes only, no placeholder code or TODO comments
- No changes without reading the relevant docs first

## Team Conventions
- PR title format: type(scope): description (matching commit convention)
- PR must include: what changed, why, how to test
- Minimum 1 reviewer approval before merge
- Squash merge feature branches into dev
- Regular merge (or rebase) dev into main for releases

Target length: 80–120 lines. Comprehensive but scannable.

Generate Canonical Docs

Creates the full documentation set that becomes the shared source of truth for the entire team.

Prompt — Generate Canonical Docs 
Generate the full canonical documentation set for this project. These docs become the shared source of truth for the entire team.

Start with an interrogation:
"Before writing any code, interrogate my idea in planning mode only. Assume nothing. Ask questions until there are no assumptions left. One question at a time."

Once the interrogation is complete, generate all six files in the project root:

**PRD.md** — Product requirements: what the product does, who it's for, core features, user stories, success criteria, explicit non-goals for v1. This is the contract for what "done" looks like.

**APP_FLOW.md** — User flows: every screen, every action, every transition. What the user sees and does, step by step. Decision points, success states, error states, and a full screen inventory with routes.

**TECH_STACK.md** — Locked dependencies: language, framework, database, auth provider, hosting, CI/CD, package manager. Exact versions. No "or" — pick one of everything. Prevents hallucinated dependencies.

**FRONTEND_GUIDELINES.md** — Design system: colors (exact hex), spacing scale, typography, component patterns, responsive breakpoints, dark/light mode rules, UI library preferences.

**BACKEND_STRUCTURE.md** — Database schema with every table, column, type, and relationship. API endpoint contracts. Authentication logic. Storage rules. Error response format.

**IMPLEMENTATION_PLAN.md** — Step-by-step build sequence. Specific steps like: 1.1 initialize project, 1.2 install deps from TECH_STACK.md, 2.1 build auth per BACKEND_STRUCTURE.md. Each step references the relevant doc. Each step is completable in a single session.

Be specific and exhaustive. No ambiguity. Docs should cross-reference each other.

After generating, update CLAUDE.md to reference all six docs and add:
- "Reference the canonical docs for all product and architecture decisions"
- "Never contradict what's in the docs — update the doc first if something needs to change"
