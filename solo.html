Real apps

01 / Character What This Looks Like

A SaaS you're building on weekends with plans to launch. A client project where you're the sole developer but there's a paying customer on the other end. An open-source tool you maintain alone that people actually depend on.

The code matters beyond today. You'll come back to it in weeks or months. Other people might read it. Bugs have consequences — not just for you, but for users or clients. You need enough structure to stay organized without the overhead of a full team process.

02 / Workflow Step by Step

Structured enough to prevent disasters. Light enough to stay productive.

Day 1

  • Initialize git repo and push to GitHub
  • Create a README.md with project description, tech stack, and how to run locally
  • Set up a basic CI pipeline — a GitHub Action that runs linting and tests on every push (even if you have zero tests at first, the pipeline is ready)
  • Enable plugins: superpowers, episodic-memory, context7, commit-commands, github
  • Generate a CLAUDE.md using the prompt below — this is your project's instruction manual for Claude
  • Use conventional commits from the start — a standardized format like feat:, fix:, chore: that makes your git history readable

Before Each Feature

  • Create a feature branch — an isolated copy of the codebase where you build one thing without affecting the stable main branch
  • Use /plan or the writing-plans skill to think through the approach before writing code
  • Write tests for the critical path first — at minimum, test that the happy path works
  • Commit frequently with clear messages: feat: add user login, fix: handle empty cart

Before Shipping

  • Open a pull request (PR) — even as a solo dev, this gives you a place to review your own changes as a batch
  • Self-review the diff: read every line you changed. Catch the dumb mistakes before they ship.
  • Squash merge into main — this collapses all your feature commits into one clean commit on the main branch
  • Verify the CI pipeline passes before merging
  • Deploy from main only

03 / Why Cost of Skipping

Feature branches One broken commit on main and your production is down
Tests on critical paths Ship a regression to your paying client, lose trust overnight
CI pipeline Merge code that doesn't even compile. Happens more than you think.
Self-review via PR Miss a console.log, a hardcoded password, or a broken import
Conventional commits Come back in 3 months to "fix stuff" and "updates" in the git log
CLAUDE.md Claude generates code that doesn't match your patterns or stack
Squash merge Main branch history becomes an unreadable mess of WIP commits

05 / Prompts Setup Prompts

Copy these into Claude Code to bootstrap your project with the right structure.

Project Bootstrap

Sets up git, CI, folder structure, and essential config for a solo project.

Prompt — Project Bootstrap 
I'm starting a serious solo project. Help me set it up with proper structure for long-term maintenance.

Ask me these three questions, then scaffold the project:

1. What are you building? (one sentence)
2. What language/framework are you using?
3. Is this a fresh repo or an existing one?

After I answer, do the following:

**Git setup:**
- Initialize git repo if fresh (or verify existing)
- Create a .gitignore appropriate for the stack
- Set up conventional commit style (I'll use /commit going forward)

**Project structure:**
- Create a README.md with: project name, description, tech stack, how to run locally, how to run tests
- Create a sensible folder structure for the framework
- Add a basic linting config if the framework supports it (ESLint, ruff, etc.)
- Set up a minimal test runner and create one example test file

**CI/CD:**
- Create a GitHub Actions workflow (.github/workflows/ci.yml) that:
  - Runs on push to main and on pull requests
  - Installs dependencies
  - Runs linting
  - Runs tests
  - Keep it under 30 lines if possible

**Session files:**
- Create a progress.txt with sections: COMPLETED, IN PROGRESS, NEXT, KNOWN BUGS (all empty to start)
- Create a lessons.md with header: "Corrections and patterns to avoid. AI reads this at session start."

**Plugins to enable:**
- superpowers, episodic-memory, context7, commit-commands, github

Make an initial commit: "chore: initial project scaffold with CI"

Do NOT set up:
- Docker or containerization
- Staging environments
- Branch protection (I'll add that manually if needed)
- Deployment pipelines (just CI for now)

Generate CLAUDE.md

Creates a project-specific CLAUDE.md so Claude understands your codebase and workflow.

Prompt — Generate CLAUDE.md 
Generate a CLAUDE.md file for this project. This file tells Claude Code how to work with this codebase.

Ask me these questions first:

1. What is this project? (one sentence)
2. What is your tech stack? (language, framework, package manager, database if any)
3. What are the most important files or directories I should know about?
4. Any hard rules Claude must never break? (e.g., "never commit to main directly", "always write tests for new features")
5. Any external services or APIs involved?

Then generate a CLAUDE.md file at the project root with this structure:

## Workflow & Behavior
- Use conventional commits via /commit for all changes
- Search episodic memory at the start of each session for prior context
- Read progress.txt and lessons.md at the start of every session
- Always create a feature branch before starting work (never commit directly to main)
- Enter plan mode (writing-plans) before implementing anything with 3+ steps
- Write tests for critical paths before marking work as done
- Self-review changes before creating a PR
- Keep commits small and focused — one logical change per commit
- After completing a feature, update progress.txt
- After any correction or debugging session, update lessons.md with the pattern and the fix
- Verify work before marking done — run tests, check the UI, confirm end-to-end
- Fix bugs autonomously when encountered — don't just report them, resolve them
- Ask before deleting files, dropping tables, or making breaking changes to APIs

## Essential Commands
[Fill based on tech stack — how to install, run dev server, run tests, lint, build]

## Architecture Overview
[Fill based on answers — folder structure, key files, data flow]

## Data Model
[Fill if relevant — database tables, key relationships, important schemas]

## Development Patterns
[Fill based on stack — naming conventions, file organization, error handling approach]

## Task Management
- Plan before building. Break features into steps.
- One feature at a time. Commit after each logical unit.
- Capture lessons in lessons.md after corrections.

## Critical Rules
[Fill based on answer to question 4, plus these defaults:]
- Never expose API keys or secrets in code
- Never skip tests to ship faster
- Always handle errors at API boundaries
- Keep dependencies minimal — don't add a library for something the language can do natively
- Simplicity first. Don't over-engineer. Minimal dependencies.
- No lazy fixes — find root causes, not workarounds

Target length: 60–100 lines. Concise but complete.

Generate Project Docs

Creates the core planning documents that become your project’s source of truth.

Prompt — Generate Project Docs 
Generate the core planning documents for this project. These docs become the source of truth that CLAUDE.md references.

Before generating, either:
- Run an interrogation first: "Interrogate my idea. Assume nothing. Ask questions until there are no assumptions left. One question at a time."
- Or answer these questions yourself if you already have clarity:
  1. Who is this for and what is the core action they take?
  2. What data needs to be saved and displayed?
  3. What happens on error vs success?
  4. What is explicitly out of scope for v1?

Then generate these three files in the project root:

**PRD.md** — Product requirements: what the product does, who it's for, core features for v1, explicit non-goals. This is the contract for what "done" looks like.

**TECH_STACK.md** — Locked dependencies: language, framework, database, auth provider, hosting, package manager. Exact versions. No "or" — pick one of everything. Prevents hallucinated dependencies.

**IMPLEMENTATION_PLAN.md** — Step-by-step build sequence. Not "build the app." Specific steps like: 1.1 initialize project, 1.2 install dependencies from TECH_STACK.md, 2.1 build auth flow, etc. Each step should be completable in a single session.

Be specific and exhaustive. No ambiguity.

After generating, update CLAUDE.md to reference these docs:
- "Read PRD.md for product requirements"
- "Follow IMPLEMENTATION_PLAN.md for build order"
- "Reference TECH_STACK.md for dependency decisions"
