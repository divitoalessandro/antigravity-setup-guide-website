01 / Foundation

Why Vibe Coding Fails — and How to Fix It

Vibe coding isn't the problem. The problem is expecting AI to fill the gaps in your thinking. AI is a translator. It converts your intent into code. When your intent is unclear, the code will be unclear. The fix isn't better prompts — it's better understanding.

The core insight: AI doesn't hallucinate because it's broken. It hallucinates because you gave it nothing to hold onto. No structure, no clarity, no foundation. Once you know what you're building, prompting becomes almost trivial — the words come naturally because you finally know what to ask for.
The Real Failure Mode

The most common pattern: open an AI tool, describe the app in one sentence, let it start coding immediately. No plan, no reference, no source of truth. Three files in, the project starts falling apart because every decision is being made by AI without constraints — and inconsistent decisions compound into chaos.

What people do
Describe a vague idea → wait for magic → get broken code → blame AI → give up or start over.
What actually works
Interrogate the idea → write documentation → use docs as constraints → build step by step.
The sequence that never fails
Interrogation → Documentation → Code. In that order. Every single time.
What You Need to Understand First

You don't need to memorize syntax. But you do need to understand the vocabulary well enough to describe your intent to AI. Every chapter in this guide builds that vocabulary. The concepts — components, state, routes, APIs — aren't abstract theory. They're the words that unlock precise, buildable prompts.

The payoff: When you understand what a component is, you stop saying "make the header." You say "build the navbar component with responsive behavior, active state for the current route, and a mobile hamburger menu." Same request — completely different output quality.
02 / Documentation System

Documentation First. Code Second. Always.

Before writing a single line of code, write your project's canonical documentation. These aren't docs for humans — they're constraints for AI. Every file you write becomes a reference that AI reads, follows, and defers to instead of guessing.

Why this works: AI operates with high capability but low certainty. Without documented constraints, it makes architectural decisions you never approved, adds features you didn't ask for, and produces code that solves problems you never articulated. Canonical docs eliminate the guessing entirely.
The Six Canonical Docs
PRD.md
Product Requirements Document
The full spec. What you're building, who it's for, what features exist, what's explicitly out of scope. User stories, success criteria, and non-goals. This is your contract. AI reads this and knows exactly what "done" looks like. Without it, you don't have an app plan — you have a wish.
APP_FLOW.md
Application Flow
Every page and every user navigation path documented in plain English. What triggers each flow. Step-by-step sequences with decision points, success states, error states, and a full screen inventory with routes. Prevents AI from guessing how users move through your app.
TECH_STACK.md
Technology Stack
Every package, dependency, API, and tool locked to exact versions. "Use React" means any version. "React 18.2.0, Next.js 14.1.0, TypeScript 5.3.3" means exactly what you specified. Eliminates hallucinated dependencies and random tech choices entirely.
FRONTEND_GUIDELINES.md
Frontend Guidelines
Your complete design system. Fonts, color palette with exact hex codes, spacing scale, layout rules, component styles, responsive breakpoints, and UI library preferences. Every visual decision locked down. AI references this for every component. No random colors, no inconsistent spacing.
BACKEND_STRUCTURE.md
Backend Structure
Database schema with every table, column, type, and relationship defined. Authentication logic, API endpoint contracts, storage rules, and edge cases. AI builds your backend against this blueprint — not against its own assumptions.
IMPLEMENTATION_PLAN.md
Implementation Plan
A step-by-step build sequence. Not "build the app." More like: step 1.1 initialize project, step 1.2 install dependencies from TECH_STACK.md, step 2.1 build navbar per FRONTEND_GUIDELINES.md. The more steps, the less AI guesses. The less AI guesses, the fewer hallucinations.
The Two Session Files

AI has no memory between sessions. When you close a terminal and open a new one, all context is gone. These two files are your persistence layer — the bridge between sessions.

CLAUDE.md
AI Operating Manual (read automatically)
Claude Code reads this file from your project root automatically at the start of every session. It contains the condensed rules from all six docs: tech stack summary, naming conventions, file structure, component patterns, and forbidden actions. After every correction you make to AI's behavior, end with: "Edit CLAUDE.md so you don't make that mistake again." Over time, CLAUDE.md becomes a self-improving rulebook — mistake rates drop measurably because AI is encoding its own corrections.
progress.txt
Session State Tracker
Tracks what's been done, what's in progress, and what's next. Update it after every completed feature. Start every new session by having AI read this file first. Without it, every session starts from zero context. With it, AI picks up exactly where you left off — no re-explaining your entire project for the 20th time.
Example progress.txt
COMPLETED: User auth via Clerk (login, signup, Google OAuth) Dashboard layout with sidebar navigation Products API endpoint (GET /api/products) IN PROGRESS: Product detail page (/products/[id]) Need to connect frontend to API endpoint NEXT: Shopping cart functionality Checkout with Stripe KNOWN BUGS: Mobile nav doesn't close after link click
The lessons.md loop: Create a lessons.md file alongside these. After every correction and debugging session, have AI update it with the pattern that caused the issue and the rule that prevents it. Reference it in CLAUDE.md: "Review lessons.md at session start." This is the self-improvement loop that makes your AI smarter about your specific project over time.
03 / The Interrogation System

Make AI Tear Your Idea Apart Before Building It

Before writing your documentation — before writing anything — use AI to interrogate your idea until there are no assumptions left. This is the step most people skip, and it's why most projects fail.

The Interrogation Prompt
Start with this
"Before writing any code, interrogate my idea in planning mode only. Assume nothing. Ask questions until there are no assumptions left. One question at a time."

AI hallucinates when your clarity ends. Extending your clarity forces AI to find the gaps in your thinking before it starts building on a broken foundation. A good interrogation session covers:

  • → Who is this for? What is the core action a user takes?
  • → What happens when they complete that action?
  • → What data needs to be saved? What data needs to be displayed?
  • → What happens on error? What happens on success?
  • → Does this need authentication? A database? Mobile support?
  • → What is explicitly out of scope for the first version?
Interrogation → Documentation

Once the interrogation is complete, use the answers as raw material for your docs. The user description feeds your PRD. The data structure feeds your BACKEND_STRUCTURE. The flows feed your APP_FLOW. Then use this second prompt to generate the full doc set in one pass:

Doc generation prompt
"Based on our interrogation, generate my canonical documentation files: - PRD.md - APP_FLOW.md - TECH_STACK.md - FRONTEND_GUIDELINES.md - BACKEND_STRUCTURE.md - IMPLEMENTATION_PLAN.md Use the answers from our conversation as source material. Be specific and exhaustive. No ambiguity."

Review every draft AI produces. Correct anything vague, add anything missing, and lock them as your source of truth. The docs cross-reference each other by design — the PRD defines features, APP_FLOW defines how users experience them, TECH_STACK defines what builds them, FRONTEND_GUIDELINES defines how they look, BACKEND_STRUCTURE defines how data works, and IMPLEMENTATION_PLAN defines the build order.

04 / Core Concepts

The Vocabulary That Makes Prompts Work

You don't need to memorize syntax. You need to understand these concepts well enough to describe them. When you know what a component, state, route, and API are, your prompts become precise and buildable instead of vague and guessable.

Components

A component is a reusable piece of interface. Think LEGO bricks — each piece is a component, you combine them to build something. A button is a component. A navigation bar is a component. A product card is a component made of smaller components (image, title, price, button).

When you say "build me a landing page," AI decides what components to create. If you don't specify, it guesses and might produce one giant unmaintainable file instead of clean, isolated, reusable pieces.
❌ Vague
"Build me a landing page"
✓ Specific
"Build a landing page with these components: Navbar, HeroSection, FeaturesGrid (3 cards), TestimonialCarousel, CTASection, Footer. Each in its own file in src/components/."
State

State is data that changes. When you click a button and something happens — state changed. When you type in a form and see your text — state changed. When you toggle dark mode — state changed. State is why your app feels alive. Without it, everything is static and nothing responds.

Common state examples
Is the menu open or closed? Is the user logged in? What items are in the cart? What text is in the input? Is this loading or done?
When buttons don't work
If a button click does nothing, it's almost always a state problem. The click happened, but nothing told the app to update.
✓ State-aware prompt
"When the user clicks the button, set modal state to open. When they click outside the modal or press Escape, set it to closed."
Layout

Every website is boxes inside boxes. Master this mental model and you understand 90% of web layout. The main structure: header at the top, main content in the middle, optional sidebar, footer at the bottom. Inside main content: sections divide the page, containers control width, grids organize into rows and columns, cards group related content.

✓ Layout-specific prompt
"Two-column layout. Left sidebar 250px wide, fixed position (doesn't scroll). Main content takes the remaining width with max-w-3xl and centered."
Pages vs Routes

A page is what the user sees. A route is the URL that shows that page. Routes can be static (/about always shows the same page) or dynamic (/products/[id] shows different products based on the ID in the URL).

✓ Routes defined upfront
"I need 4 pages: home (/), about (/about), products listing (/products), single product (/products/[id]). Create the file structure and navigation links."
05 / Styling & Design

Making It Look Good — Deliberately

Styling is not an afterthought. It's a decision you make once, document in FRONTEND_GUIDELINES.md, and enforce consistently across every component. When every element uses the same design tokens, your app feels cohesive. When each component invents its own values, it looks like five different people built it.

UI vs UX
UI — What it looks like
Colors, fonts, button shapes, spacing, visual hierarchy. "Make it look better" is a UI request.
UX — How it feels to use
Can someone figure out what to do? Is the flow intuitive? Are people frustrated or delighted? "Make it easier to use" is a UX request.
Screenshot references are faster than words. Find a UI you love, screenshot it, feed it directly to Claude Code or Cursor. Prompt: "match this layout" or "use this UI as reference." AI can extract design patterns, spacing, color palettes, and component structures from a screenshot more accurately than from a written description.
Design Tokens — The Foundation of Consistency

Design tokens are consistent values you reuse everywhere. Your brand color isn't "any blue" — it's the same hex code on every element. Your spacing isn't random — it's always multiples of 4px. Lock these in FRONTEND_GUIDELINES.md before writing the first component:

Token definition example
Colors: primary #3B82F6, background #0F0F11, surface #18181B, text #F4F4F5, muted #71717A Spacing scale: 4px, 8px, 12px, 16px, 24px, 32px, 48px, 64px Border radius: sm 4px, md 8px, lg 12px, full 999px Shadows: sm / md / lg with specific values Transitions: 150ms ease for interactions
Design Languages Worth Knowing

Reference these by name in prompts and FRONTEND_GUIDELINES.md. Precise vocabulary unlocks specific, recognizable aesthetics instead of vague approximations.

Glassmorphism
Frosted glass effect. Translucent elements with background blur, subtle borders, soft shadows. Cards, modals, navigation bars. Risk: low contrast — keep text readable.
Neobrutalism
Raw, bold, intentionally unpolished. High-contrast colors, thick black borders, flat shadows, clashing palettes. Works for creative brands, indie tools, portfolios.
Bento Grid
Modular layouts with blocks of varying sizes. Big cards for important content, smaller for secondary. Responsive by nature. Perfect for dashboards, feature showcases.
Dark Mode System
Not just a toggle — a full design system. Define both light and dark palettes in FRONTEND_GUIDELINES.md before coding. Don't add it as an afterthought.
Micro-interactions
Subtle animations that respond to user actions. A button that scales on hover. A checkbox that bounces. These details separate polished from amateur.
Kinetic Typography
Text that moves, reacts to scroll or cursor. Use sparingly for hero sections and key moments. CSS transitions and Framer Motion make this achievable.
✓ Design-specific prompt
"Glassmorphism cards with bento grid layout, dark mode, micro-interactions on hover states. Reference colors and spacing from FRONTEND_GUIDELINES.md."
Responsive Design

Responsive means your site works on all screen sizes. Mobile-first is not a preference — it's a strategy. Building mobile-first forces you to prioritize content. What absolutely must be on the small screen? That's your core. Everything else is progressive enhancement.

Breakpoints
Mobile: 0–640px · Tablet: 640–1024px · Desktop: 1024px+. Define these in FRONTEND_GUIDELINES.md and reference them in every layout decision.
Tailwind mobile-first
Unprefixed styles apply to all screens. md: and lg: kick in at breakpoints. flex flex-col md:flex-row = stacked mobile, side-by-side tablet+.
50%+ of your users are on phones. If you only test on your laptop, you're shipping a broken experience for most people. Test on mobile after every major component is built — not just before shipping.
06 / Architecture

Frontend, Backend, APIs, and Data

Understanding how the pieces connect lets you tell AI exactly what to build and where to put it. The more specific you are about architecture, the less AI invents its own.

Frontend vs Backend
Frontend
What users see and interact with. Runs in the browser. The interface, UI components, page routing, visual state. No database access directly.
Backend
What happens behind the scenes. Server-side logic, database access, authentication, business rules. Users never touch this directly.
The flow
Frontend collects input → sends to server → server validates and saves → sends confirmation → frontend shows result.
Never validate only on the frontend. Frontend validation is a convenience for users. Backend validation is security. Always validate inputs on the server — don't trust anything coming from the browser.
APIs

An API is how two systems talk to each other. Your frontend needs data from your backend — it asks via an API. Your app needs to process payments — it talks to Stripe via their API. Think of it as a waiter: you tell the waiter what you want, the waiter goes to the kitchen, brings back your order.

GET
Retrieve data. Fetching a list of products, loading a user profile.
POST
Send new data. Submitting a form, creating a new record.
PUT / PATCH
Update existing data. Editing a profile, changing a status.
DELETE
Remove data. Deleting a post, canceling an order.
Databases

A database is where you save things permanently. Without one, everything resets on refresh. Use Supabase as your default — it handles both database and auth, has a generous free tier, and is designed for exactly this kind of workflow.

When you need a database
Users can create accounts. Users can save their own content. Submissions need to be stored. Data grows over time.
When you don't
Static site, same content for everyone. Portfolio with no user interaction. Landing page that just collects emails via a form service.
Authentication

Authentication (login/logout) is harder than it looks. Passwords need encryption, sessions need management, tokens need handling. Don't build auth from scratch. Use a service. Clerk is the simplest with great UI out of the box. Supabase Auth works if you're already using Supabase.

One of the most common security mistakes is implementing auth manually without fully understanding the implications. The time you "save" by rolling your own auth is paid back tenfold in security vulnerabilities. Use a proven service and configure it.
Folder Structure

A messy project confuses AI. When files are scattered arbitrarily, AI puts new files in random locations and nothing connects properly. Always tell AI where to put things, and lock the structure in your CLAUDE.md.

my-app/ ├── src/ │ ├── app/ → pages and routes │ ├── components/ → reusable UI pieces │ ├── lib/ → utilities and helpers │ └── styles/ → CSS files ├── public/ → images and static files ├── .env → secrets (NEVER commit) ├── CLAUDE.md → AI rules and context ├── progress.txt → session tracking ├── PRD.md → product requirements ├── APP_FLOW.md → user flows ├── TECH_STACK.md → locked dependencies ├── FRONTEND_GUIDELINES.md → design system ├── BACKEND_STRUCTURE.md → database and API spec └── IMPLEMENTATION_PLAN.md → build sequence
07 / The Toolbox

The Right Tool for Each Phase

You don't need 50 tools. You need the right tools used at the right time. The difference between someone who ships and someone who's stuck isn't which AI model they use — it's knowing which model to use when.

AI Coding Tools
Cursor Build
AI-native editor that sees your entire project, understands file relationships, and can edit across multiple files at once. Four distinct modes for different phases.
Use for: general implementation, multi-file edits, the core coding workflow
Claude / Claude Code Think
Your thinking partner. Use for interrogation, writing canonical docs, planning architecture, complex product decisions. Claude Code runs in your terminal and auto-reads CLAUDE.md.
Use for: docs, planning, architecture, documentation-heavy tasks
Kimi K2.5 Design
Native multimodal model. Feed it a screenshot, video, or design mockup and it generates frontend code that closely matches the visual. Where other models approximate, K2.5 replicates.
Use for: visual-heavy frontend work, design-to-code translation
Codex Debug
OpenAI's coding agent. Each task gets its own isolated sandbox preloaded with your repo. Reads your codebase, traces dependencies, proposes fixes across files. Can run tests and iterate until they pass.
Use for: debugging, code review, finalizing before shipping
Cursor's Four Modes
Ask
Read-only exploration
AI reads your codebase and answers questions without changing anything. Use it when you're exploring unfamiliar code, understanding how something works, or planning before touching files. "What does this function do?" "Why is this component re-rendering?" "What would break if I changed this?"
Plan
Architect before you code
Describe what you want to build. Cursor creates a detailed implementation plan, asks clarifying questions, and can generate diagrams. Use at the start of every new feature. Review, adjust, approve — then hand to Agent mode. Also use Plan mode for verification: "Plan how to verify that this auth flow handles all edge cases."
Agent
Autonomous implementation
AI writes code, edits files, runs terminal commands, installs packages, and fixes errors autonomously. Reads your entire project, follows your rules files, and implements features end-to-end. This is where most vibe coding happens.
Debug
Structured debugging loop
For stubborn bugs. Instruments your code with runtime logs, generates multiple hypotheses, asks you to reproduce the bug, tests its fix, asks you to verify. More systematic than guessing — use this when a bug survives two or three regular fix attempts.
Infrastructure Stack
GitHub Version Control
Where your code lives in the cloud with every change tracked. Non-negotiable. Without it, one mistake can destroy everything. With it, you can go back to any previous state in seconds.
Vercel Deploy
Push to GitHub, Vercel automatically builds and deploys. You get a live URL. Free tier is generous. From your computer to live on the internet in minutes with zero config.
Supabase Database + Auth
Free tier, good docs, handles database and auth in one place. If you're not sure what backend to use, use Supabase. It gets out of your way so you can focus on the product.
Advanced Workflow: Parallel Sessions

Once you've built a few projects with the basic system, these techniques multiply your speed significantly.

Git worktrees are the single biggest productivity unlock. Spin up 3–5 worktrees, each running its own Claude Code session in parallel. One builds auth, another builds the dashboard layout, a third handles API endpoints. All share the same repo but work independently. What used to take a full day of sequential building becomes a few hours of parallel execution.
Subagents for complex problems. When a problem is big enough that one Claude session would choke on context, append "use subagents" to your request. Claude spins up focused sub-sessions for parallel analysis while keeping your main context window clean. One task per subagent. Think of it as delegating to a team.
Voice dictation for better prompts. You speak 3× faster than you type, and your prompts get dramatically more detailed as a result. On macOS, press fn fn to start dictating. Longer, more detailed prompts produce better outputs — voice is the shortcut to getting there without the friction.
08 / The Build Loop

Git, Deploy, Debug, Iterate

Vibe coding is not a one-shot approach. It's iteration. The skill is iterating quickly and knowing which tool to use at each step — not avoiding iteration entirely, and not getting stuck in loops of the same broken code.

Git — Commit Early and Often

Git tracks every change. Without it: you break something and can't undo it. With it: every change is saved, you can return to any previous state, and your code lives on GitHub — not just your computer.

Core git commands
git add . # stage changes git commit -m "feat: add user login" # save with message git push # upload to GitHub git pull # download latest changes
Commit after every major feature that works. If you break something, you can always roll back. The message matters too — use Conventional Commits: feat: add X, fix: resolve Y, refactor: clean up Z. Your AI can write these for you: "Write a clear git commit message for these changes following Conventional Commits."
Environment Variables — Never Expose Secrets
Never put API keys in your code. They go in a .env file, accessed via process.env.YOUR_KEY_NAME. Add .env to .gitignore. Never paste API keys in screenshots or AI chat. If you commit a key to a public repo, assume it's compromised immediately — go revoke it and create a new one. When deploying to Vercel, add environment variables in Vercel's dashboard — they don't transfer from your local .env automatically.
Reading Error Messages

Errors are instructions, not insults. They tell you exactly what went wrong. Read them. An error message has three parts: the type, the description, and the location.

Anatomy of an error
TypeError: Cannot read property 'map' of undefined at ProductList (src/components/ProductList.tsx:15:23) → TypeError: using something in the wrong way → 'map' of undefined: called .map() on something that doesn't exist yet → ProductList.tsx:15:23: exact file and line number to investigate
✓ How to give AI an error
"I'm getting this error: [full error message and stack trace]. Here's the code at that line: [paste relevant code]. I expected it to [what you expected]."
The Debugging Loop
  1. Read the error message. Actually read it.
  2. Find the location. What file, what line number.
  3. Understand the claim. What does the error say is wrong?
  4. Check the obvious first. Typos, missing imports, wrong variable names.
  5. Give AI context: error + code + what you expected to happen.
  6. If it survives 2–3 rounds, switch to Cursor Debug mode or Codex. Don't keep throwing the same fix at the same bug.
How to Iterate Well

Nobody's first output is right. That's normal and expected. The skill is iterating quickly with specificity.

❌ Bad iteration
"It doesn't look right, fix it."
✓ Good iteration
"The product grid shows 4 columns on desktop but I need 3. The card images are stretched — they should be object-cover. And there's no loading state while data is fetching."
Breaking Big Ideas into Small Pieces

AI struggles with large, vague requests. "Build me a full e-commerce site" produces garbage. Break everything into pieces — each one is a single conversation or single task, each builds on the last, and each can be tested independently. This is exactly what your IMPLEMENTATION_PLAN.md already contains.

✓ Execution prompt
"Read CLAUDE.md and progress.txt first. Then build step 4.2 from IMPLEMENTATION_PLAN.md only. Style per FRONTEND_GUIDELINES.md. Stop after that step and report what was built."
09 / Shipping & Maintaining

When to Ship, and How to Keep It Running

The best app you never ship is worse than the average app that's live. Know when you're done. Know how to keep the project alive after it ships.

Verify Before You Ship
  • ✓ Does it work on mobile? Actually open it on your phone.
  • ✓ Does it work in different browsers?
  • ✓ What happens with no data? Are empty states handled?
  • ✓ What happens with wrong data? Are error states handled?
  • ✓ What happens with slow internet? Are loading states in place?
  • ✓ Can you break it by clicking fast or submitting twice?
  • ✓ Are all secrets hidden from browser dev tools?
Definition of Done
You're done when
The core feature works. Users can complete the main action. It doesn't break on common paths. It's deployed and accessible.
You're NOT done when
It's "perfect." Every edge case is handled. It has every feature you imagined. It looks exactly like a Dribbble mockup.
Ship the simple version and get real feedback. Then improve based on actual usage patterns, not hypothetical ones. A never-ending feature list kills more projects than bad code does.
Deployment with Vercel
  1. Push code to GitHub
  2. Connect the GitHub repo to Vercel (one-time setup)
  3. Vercel automatically builds and deploys on every push
  4. Add environment variables in Vercel's dashboard (not from your local .env)
  5. You get a live URL at your-app.vercel.app within minutes
99% of deploy bugs are either missing environment variables or wrong build settings. When something works locally but breaks on Vercel, paste the Vercel error logs to AI: "It works on localhost but breaks on Vercel. Here's the error from Vercel's build logs:"
Maintaining What You Built

Good documentation makes returning to a project 10× faster. Bad documentation means starting over. When you come back after three months:

✓ Session restart prompt
"Read CLAUDE.md, progress.txt, and PRD.md. I'm returning to this project after a break. Summarize where things stand against IMPLEMENTATION_PLAN.md and what needs attention next."

Treat your codebase like a home that someone unfamiliar will need to navigate. Keep dependencies updated, write comments on non-obvious logic, use consistent naming, and update your documentation every time something meaningful changes.

Third-Party Services — Use Them

Your core product is the unique thing you're building. Everything else is infrastructure. Use existing services for infrastructure — they've solved these problems better than you'll solve them in a week.

Auth
Clerk (simplest, great UI), Supabase Auth (if already on Supabase)
Payments
Stripe. The standard. Don't reinvent payment processing.
Email
Resend or SendGrid for transactional email.
File uploads
Uploadthing or Supabase Storage for media.
Components
shadcn/ui — copies code into your project, you own it, fully customizable.
Icons / Fonts
Lucide React for icons. Google Fonts or Geist for typography.
10 / The Complete System

The Full Checklist — Start to Ship

Vibe coding is meticulous planning, systems, documentation, vocabulary, and iteration. Here's the complete reference. Bookmark it, come back to it at the start of every project.

Before Building
  • 01 Run the interrogation prompt. Let AI tear your idea apart with questions until no assumptions remain.
  • 02 Answer every question. Clarity now prevents guesswork later.
  • 03 Generate the six canonical docs: PRD.md, APP_FLOW.md, TECH_STACK.md, FRONTEND_GUIDELINES.md, BACKEND_STRUCTURE.md, IMPLEMENTATION_PLAN.md.
  • 04 Write CLAUDE.md with project rules, references to all six docs, and a lessons.md self-improvement loop.
  • 05 Create progress.txt with your starting state.
  • 06 Gather UI screenshots for visual reference.
  • 07 Initialize git and push initial commit to GitHub.
While Building
  • → AI reads CLAUDE.md, progress.txt, and lessons.md first, every session.
  • → Use Ask and Plan modes to architect before coding. Never jump straight to Agent.
  • → Match tool to task: K2.5 for visual frontend, Claude Code for architecture, Cursor Agent for general implementation.
  • → Work in small pieces. One feature at a time. One step from IMPLEMENTATION_PLAN.md at a time.
  • → Use screenshot references for all UI work.
  • → Commit to git after each working feature.
  • → Update progress.txt after each feature.
  • → After every correction, update CLAUDE.md and lessons.md so AI never makes the same mistake twice.
  • → Test on mobile regularly — not just at the end.
Before Shipping
  • ✓ Test on an actual mobile device.
  • ✓ Verify error states and empty states are handled.
  • ✓ Confirm all secrets are hidden from the browser.
  • ✓ Walk through the main user flow end-to-end.
  • ✓ Check performance — is anything noticeably slow?
  • ✓ Use Codex to debug, review, and finalize.
After Shipping
  • → Update docs to reflect what was actually built.
  • → Update dependencies periodically — outdated packages have known vulnerabilities.
  • → Iterate based on real user feedback, not hypothetical scenarios.
  • → Keep progress.txt and lessons.md current for future sessions.
  • → Turn repeated workflows into reusable skills and slash commands.
The summary in one line: Claude does the thinking. Cursor builds. Kimi K2.5 handles visual frontend. Codex debugs and finishes. GitHub tracks everything. Vercel ships it. You provide the direction, vocabulary, and iteration. The AI does the typing.
