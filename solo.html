Real apps

01 / Character What This Looks Like

A SaaS you're building on weekends with plans to launch. A client project where you're the sole developer but there's a paying customer on the other end. An open-source tool you maintain alone that people actually depend on.

The code matters beyond today. You'll come back to it in weeks or months. Other people might read it. Bugs have consequences — not just for you, but for users or clients. You need enough structure to stay organized without the overhead of a full team process.

02 / Workflow Step by Step

Structured enough to prevent disasters. Light enough to stay productive.

Day 1

  • Run the 7-step Setup Procedure below first — it generates your canonical docs, CLAUDE.md, progress.txt, and initial commit before any product code is written
  • Initialize git repo and push to GitHub
  • Create a README.md with project description, tech stack, and how to run locally
  • Set up a basic CI pipeline — a GitHub Action that runs linting and tests on every push (even if you have zero tests at first, the pipeline is ready)
  • Enable plugins: superpowers, episodic-memory, context7, commit-commands, github
  • Generate a CLAUDE.md using the prompt below — this is your project's instruction manual for Claude
  • Use conventional commits from the start — a standardized format like feat:, fix:, chore: that makes your git history readable

Before Each Feature

  • Create a feature branch — an isolated copy of the codebase where you build one thing without affecting the stable main branch
  • Use /plan or the writing-plans skill to think through the approach before writing code
  • Write tests for the critical path first — at minimum, test that the happy path works
  • Commit frequently with clear messages: feat: add user login, fix: handle empty cart

Before Shipping

  • Open a pull request (PR) — even as a solo dev, this gives you a place to review your own changes as a batch
  • Self-review the diff: read every line you changed. Catch the dumb mistakes before they ship.
  • Squash merge into main — this collapses all your feature commits into one clean commit on the main branch
  • Verify the CI pipeline passes before merging
  • Deploy from main only

03 / Why Cost of Skipping

Feature branches One broken commit on main and your production is down
Tests on critical paths Ship a regression to your paying client, lose trust overnight
CI pipeline Merge code that doesn't even compile. Happens more than you think.
Self-review via PR Miss a console.log, a hardcoded password, or a broken import
Conventional commits Come back in 3 months to "fix stuff" and "updates" in the git log
CLAUDE.md Claude generates code that doesn't match your patterns or stack
Squash merge Main branch history becomes an unreadable mess of WIP commits

05 / Setup Procedure Before Building

Seven steps, run in order, before any product code is written. This procedure mirrors the Vibe 101 checklist — scoped to a serious solo build.

Before you start, enable these plugins: superpowers, episodic-memory, context7, commit-commands, github.

01 — Interrogate the Idea

Make AI tear the idea apart before any code or doc gets written. Run this in planning mode only. Answer one question at a time until no assumptions remain.

Prompt — Interrogation 
Before writing any code or docs, interrogate my idea in planning mode only. Assume nothing. Ask questions until there are no assumptions left. One question at a time.

Cover at minimum:
- Who is this for and what is the core action they take?
- What happens on success? On error?
- What data is saved? What is displayed?
- Auth, database, mobile support — needed?
- What is explicitly out of scope for v1?

Do not start writing docs until I confirm the interrogation is complete.

02 — Answer Every Question

No prompt for this step — just discipline. Clarity now prevents guesswork later. Cover every category below in plain English. Your answers become the raw material for the docs in step 03.

  • Audience and core user action
  • Success states, error states, edge cases
  • Data model: what is saved, displayed, computed
  • Authentication and third-party services
  • Out-of-scope list for v1

03 — Generate the Canonical Docs

Documentation first. Code second. Always. For a solo build, three docs cover the essentials. If you want the full six-doc set (APP_FLOW, FRONTEND_GUIDELINES, BACKEND_STRUCTURE), see the Vibe 101 documentation system.

Prompt — Generate Project Docs 
Based on our interrogation, generate these three canonical documentation files at the project root. Use the answers from our conversation as source material. Be specific and exhaustive. No ambiguity. Each doc should cross-reference the others.

**PRD.md** — Product requirements: what the product does, who it's for, core features for v1, explicit non-goals. This is the contract for what "done" looks like.

**TECH_STACK.md** — Locked dependencies: language, framework, database, auth provider, hosting, package manager. Exact versions. No "or" — pick one of everything. Prevents hallucinated dependencies.

**IMPLEMENTATION_PLAN.md** — Step-by-step build sequence. Specific steps like: 1.1 initialize project, 1.2 install dependencies from TECH_STACK.md, 2.1 build auth flow, etc. Each step references the relevant doc. Each step is completable in a single session.

04 — Write CLAUDE.md (+ lessons.md)

Now that the docs exist, distil their rules into a CLAUDE.md Claude reads at session start. Create lessons.md alongside it — the self-improvement loop that makes AI smarter about your codebase.

Prompt — Generate CLAUDE.md + lessons.md 
Generate a CLAUDE.md at the project root and an empty lessons.md alongside it. CLAUDE.md must reference PRD.md, TECH_STACK.md, and IMPLEMENTATION_PLAN.md and condense their rules into Claude-readable instructions.

Structure:

## Workflow & Behavior
- Read CLAUDE.md, progress.txt, and lessons.md at the start of every session
- Reference PRD.md for product decisions, TECH_STACK.md for dependency choices, IMPLEMENTATION_PLAN.md for build order — never contradict them; update the doc first if something needs to change
- Use conventional commits via /commit
- Always create a feature branch before starting work — never commit directly to main
- Enter plan mode (writing-plans) before implementing anything with 3+ steps
- Write tests for critical paths before marking work as done
- Self-review changes before creating a PR
- Keep commits small, focused, one logical change per commit
- After completing a feature, update progress.txt
- After every correction or debugging session, update lessons.md with the pattern that caused the issue and the rule that prevents it
- Verify before marking done — run tests, check the UI, confirm end-to-end
- Fix bugs autonomously — don't just report them, resolve them
- Ask before deleting files, dropping tables, or making breaking changes to APIs

## Essential Commands
[Fill from TECH_STACK.md — install, dev server, test, lint, build]

## Architecture Overview
[Summarise — folder structure, key files, data flow]

## Critical Rules
[Distil from PRD.md non-goals plus:]
- Never expose API keys or secrets in code — environment variables only
- Never skip tests to ship faster
- Always handle errors at API boundaries
- Keep dependencies minimal — don't add a library for something the language can do natively
- Simplicity first. No lazy fixes — root causes only.

Also create lessons.md with this header and nothing else:
"Corrections and patterns to avoid. AI reads this at session start. Update after every debugging session with: (1) the pattern that caused the issue, (2) the rule that prevents it."

Target CLAUDE.md length: 60–100 lines. Concise but complete.

05 — Create progress.txt

The session-state tracker. AI has no memory between sessions; this file is the bridge. Update it after every completed feature.

Prompt — Create progress.txt 
Create a progress.txt file at the project root with exactly this structure (sections empty to start). I will update it after every completed feature, and AI must read it at the start of every session.

COMPLETED:

IN PROGRESS:

NEXT:

KNOWN BUGS:

Then add a line to CLAUDE.md confirming: "Read progress.txt at session start; update it after every completed feature."

06 — Gather UI Screenshots

Visual references prevent AI from inventing UI from scratch. Collect screenshots of patterns you want to mimic before any frontend work begins.

Prompt — Set up screenshots folder 
Set up a /screenshots folder at the project root and walk me through what to collect.

Required references (3–5 minimum):
- Apps with similar user flows to ours
- Components I want to mimic: navigation, forms, empty states, loading states
- Color palettes and typography I like
- Mobile references for responsive behaviour

File-naming convention: kebab-case, descriptive — dashboard-ref.png, button-states.png, mobile-nav.png.

Then add this line to CLAUDE.md: "When building UI, reference /screenshots before generating new visuals. Match the established visual language; do not invent."

07 — Initialize Git & Push

Lock everything you've created into version control. The initial commit captures docs, CLAUDE.md, progress.txt, and the screenshots folder before a single line of product code is written.

Prompt — Git init & first push 
Initialize git for this project and push to GitHub.

- Initialize a git repo if one doesn't exist.
- Create a .gitignore appropriate for the stack (reference TECH_STACK.md).
- Create a README.md with: project name, one-line description, tech stack, how to run locally, how to run tests.
- Stage everything created so far: PRD.md, TECH_STACK.md, IMPLEMENTATION_PLAN.md, CLAUDE.md, lessons.md, progress.txt, /screenshots, README.md, .gitignore.
- Initial commit: "chore: initial scaffold with canonical docs".
- Help me create a new GitHub repo and push.

07b — Project Tooling Optional

Not part of the canonical Vibe 101 procedure, but worth doing for a serious solo project: linting, test runner, CI. Run after step 07.

Prompt — Solo tooling layer 
Set up the optional tooling layer for this solo project.

- Linting config (ESLint, ruff, etc.) with sensible defaults.
- Minimal test runner with one example test file.
- GitHub Actions workflow (.github/workflows/ci.yml) that runs on push and PRs: install deps → lint → test. Keep under 30 lines.
- Configure conventional commits — I'll use /commit going forward.

Commit: "chore: add CI and linting".

Do NOT set up: Docker, staging environments, branch protection, deployment pipelines.
