Weekend projects

01 / Character What This Looks Like

A Saturday afternoon CLI tool. A browser extension you build to scratch your own itch. A framework tutorial you follow along with. You're the only person who will ever touch this code, and the goal is learning or solving a personal problem — not shipping to users.

These projects live fast. You want to move quickly, try things, break things, and not worry about process slowing you down. The danger isn't lack of process — it's abandoning projects because you over-engineered the setup.

02 / Workflow Step by Step

Three phases. Keep it lightweight.

Day 1

  • Run the 7-step Setup Procedure below first — even at hobby scale, the docs and CLAUDE.md save hours later
  • Create a new folder and run git init — this tracks every change you make so you can always go back
  • Push to GitHub with a basic README.md explaining what the project is in one sentence
  • Enable episodic-memory and commit-commands plugins in Claude Code
  • Start building. No branches, no CI, no config files. Just code.

Before Each Feature

  • Commit what you have — even if it's messy. Small commits let you undo mistakes.
  • Use /commit to let Claude handle the commit message
  • Don't overthink structure. If it works, move on.

Before Sharing or Shelving

  • Manual test: open it, click around, make sure nothing is obviously broken
  • Update the README if the project scope changed
  • Push to GitHub so it's backed up and shareable

03 / Why Cost of Skipping

Git init on day one Without it, you can't undo mistakes or recover deleted code
Frequent commits Lose an afternoon of work to one bad refactor
Push to GitHub Laptop dies, project dies with it
README Come back in 3 months and have no idea what this project does
Episodic memory Claude forgets your entire context between sessions

05 / Setup Procedure Before Building

Seven steps, run in order, before any product code is written. This procedure mirrors the Vibe 101 checklist — scoped down for hobby builds. Same skeleton as solo and team, lighter prompts.

Before you start, enable these plugins: episodic-memory, commit-commands.

01 — Interrogate the Idea

Even at hobby scale, a 60-second interrogation prevents an afternoon of guesswork. Three or four questions is enough.

Prompt — Quick Interrogation 
Before I start coding, ask me 3–4 quick questions to make sure my idea is clear. One question at a time.

Cover:
- Who is this for and what is the one core action they take?
- What is the simplest version that would still be useful?
- What is explicitly out of scope?

Do not start writing anything until I confirm the answers are good.

02 — Answer Every Question

No prompt for this step — just answer plainly. Your answers feed step 03.

  • The audience and the one core action
  • The simplest useful version
  • What you are explicitly not building

03 — Generate the Canonical Docs

For a hobby build, one doc is enough: a PRD that captures what you're building. If the project grows up, see the full six-doc set.

Prompt — Generate PRD.md 
Based on our interrogation, generate a PRD.md at the project root.

**PRD.md** — Product requirements: what the product does, who it's for, the one core feature for v1, and an explicit non-goals list. Keep it short — under 40 lines. This is the contract for what "done" looks like for v1.

Be specific. No vague language like "the app should be fast" — say what fast means.

04 — Write CLAUDE.md (+ lessons.md)

Tell Claude how to work with this codebase. Keep it short. Add lessons.md so corrections compound over sessions.

Prompt — Generate CLAUDE.md + lessons.md 
Generate a CLAUDE.md at the project root and an empty lessons.md alongside it.

Ask me these questions first:
1. What is this project? (one sentence)
2. What is your tech stack? (language, framework, package manager)
3. Any hard rules Claude must never break?

Then generate CLAUDE.md with this structure:

## Workflow & Behavior
- Read CLAUDE.md, progress.txt, and lessons.md at the start of every session
- Reference PRD.md for product decisions
- Always commit with conventional commit messages using /commit
- Search episodic memory at the start of each session for prior context
- Keep changes small — one feature or fix per session
- Don't over-engineer. This is a hobby project. Simple > clever.
- After every correction, update CLAUDE.md and lessons.md so the same mistake isn't repeated
- Ask before deleting files or making breaking changes

## Coding Discipline
- Think before coding: state assumptions, present alternatives when ambiguous, push back when a simpler approach exists, ask when unclear — never pick silently
- Simplicity first: no features beyond what was asked, no abstractions for single-use code, no speculative flexibility, no error handling for impossible scenarios
- Surgical changes: every changed line must trace to the request; don't refactor, reformat, or "improve" adjacent code; match existing style even if you'd do it differently
- When you notice unrelated dead code, mention it — don't delete it. Remove only orphans your own changes created
- Goal-driven execution: turn tasks into verifiable goals ("Fix bug X" → "write a test that reproduces it, then make it pass")
- For 3+ step tasks, state a brief plan with an explicit verify check after each step

## Essential Commands
[Fill based on tech stack — how to run, build, test]

## Architecture Overview
[Brief — folder structure and key files]

## Critical Rules
[From answer to question 3, plus sensible defaults]

Also create lessons.md with this single header line:
"Corrections and patterns to avoid. AI reads this at session start. Update after every correction with the pattern that caused the issue and the rule that prevents it."

Keep CLAUDE.md under 70 lines. No boilerplate padding.

05 — Create progress.txt

So the next session doesn't start from zero context.

Prompt — Create progress.txt 
Create a progress.txt file at the project root with exactly this structure (sections empty to start):

COMPLETED:

IN PROGRESS:

NEXT:

KNOWN BUGS:

Then add a line to CLAUDE.md: "Read progress.txt at session start; update it after every completed feature."

06 — Gather UI Screenshots

Even one or two visual references stop AI from inventing UI from scratch.

Prompt — Set up screenshots folder 
Create a /screenshots folder at the project root.

I will save 2–3 visual references there: apps with similar flows, components I want to copy, or color palettes I like. Use kebab-case names: ref-dashboard.png, ref-button.png.

Add this line to CLAUDE.md: "Reference /screenshots before generating any UI."

07 — Initialize Git & Push

Lock everything in version control before product code starts. Even a hobby project deserves a backup.

Prompt — Git init & first push 
Initialize git for this project and push to GitHub.

- Initialize a git repo if one doesn't exist.
- Create a .gitignore appropriate for the language/framework.
- Create a README.md with: project name, one-line description, tech stack, "Getting Started" section.
- Stage everything: PRD.md, CLAUDE.md, lessons.md, progress.txt, /screenshots, README.md, .gitignore.
- Initial commit: "chore: initial scaffold".
- Help me push to a new GitHub repo.

Do NOT set up CI, testing frameworks, branch protection, Docker, or linting configs. Keep it simple — start coding in under 2 minutes from here.
